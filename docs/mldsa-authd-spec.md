# mldsa-authd — deployment specification (v1 draft, V4-3)

## 0. Status and relationship to the protocol specification

This document specifies **`mldsa-authd`**, a daemon that uses the protocol of
[ml-dsa-auth-protocol-spec-v2.md](ml-dsa-auth-protocol-spec-v2.md) as the
login mechanism for **one website**, plus the identity lifecycle, storage and
local API that a deployment needs and the protocol deliberately leaves out.

**Nothing on the wire changes.** Every handshake and record byte is spec-v2's.
This document adds only what sits *above* the record layer (application
messages), *beside* it (a store, a local API, a key envelope) and *around* it
(deployment). Where the two documents disagree about anything in spec-v2's
scope, **spec-v2 wins** and this document is wrong.

Spec-v2 is frozen. This document is versioned independently and is written
before the implementation, as spec-v2 was: an exit criterion for each build
step, not a description of code that already exists.

Milestones: **A** — operators (a handful of identities the operator controls,
native CLI). **B** — public end users from browsers. Sections marked *(B)*
are not implemented in milestone A.

## 1. Objective

Let a person prove to one website that they hold a device key, over a channel
that is confidential against a future quantum adversary, without the site ever
storing a secret that could impersonate them, and without a password.

Concretely, after a successful handshake the daemon issues a short-lived
**login code**; the site exchanges that code over a local socket for an opaque
**session token** which it sets as a cookie. The site's own session mechanics
are unchanged and out of scope.

## 2. Scope

**In scope:** the daemon (event loop, connection state machine, WebSocket
binding, rate limiting); the identity lifecycle (enrollment, rotation,
revocation, recovery); the store; tokens; key encryption at rest; the local
API; the operator CLI; the browser client *(B)*; deployment and logging.

**Out of scope, explicitly:** server identity-key rotation (planned separately;
today it means redistributing pins); HSM or TPM key custody; federation or
multiple relying parties; multi-party sessions; thread safety (the daemon is
single-threaded by construction, spec-v2 §6.3.6); WebAuthn/CTAP interoperability;
the site's own authorization model; anything about what a session may *do*
once established.

## 3. Identifiers

### 3.1 Device handle

The wire identity (spec-v2's `client_id`) is a **device handle**, not a user
name:

```
handle = "d1" || 32 lowercase hex characters       (34 bytes)
```

The 16 random bytes are generated by the client together with its keypair, so
no round trip is needed to learn an identity. 34 bytes is within
`WIRE_ID_MAX_LEN` (64) and passes `demo_keys_id_filename_safe`, so a handle can
name a key file.

Consequences, all deliberate: a handle carries no user name, so the wire
reveals no account; handles are unguessable (128 bits), which is most of the
answer to enumeration (§5 Req 9); and a *user* is a daemon-level grouping of
handles, never a wire identity.

### 3.2 User id, labels, roles

`user_id` is an opaque byte string, 1..64 bytes, chosen by the site. `label` is
free-form UTF-8, ≤ 64 bytes, shown to the user ("work laptop"); it is never
compared and never on the wire. `role` is `operator` or `user`.

Identities and labels are **attacker-influenced strings**. Anywhere they are
logged or displayed they are escaped exactly as `apps/demo_app.c`'s
`format_id` does: printable ASCII as-is, everything else as `\xHH`.

## 4. Trust model

The **site is the relying party and the trusted enroller.** It decides who may
enroll a device and it consumes tokens. It never holds key material.

The **server identity key** is pinned by every client. A client MUST reject a
`ServerHello` that is not signed by the pinned key (spec-v2 §6.3, responder
identity binding) — this is what makes the deployment phishing-resistant, and
it is cryptographic, not string matching against an origin.

Clients obtain the server's public key **out of band over a channel already
trusted by other means** (spec-v2 §6.2) — in practice, fetched from the site
over TLS at enrollment and pinned thereafter (TOFU-over-TLS).

What a **compromised site process** can do: enroll devices for any user, read
tokens it is given, revoke anything. What it cannot do: obtain any device or
server secret, or mint a token without a completed handshake — a token exists
only after `EXCHANGE` of a login code that only a successful handshake
produces. What **root on the host** can do: everything; see
[v4/threat-model.md](v4/threat-model.md).

## 5. Security requirements

Normative. Each is numbered so it can be pinned by a named test, fuzz oracle or
tool, and so an external reviewer can check them one at a time. The V4-1 audit
found two requirements in spec-v2 pinned by nothing; this document starts with
none, and the step that implements a requirement ships its pin.

1. **No new cryptographic primitives.** Everything is liboqs or libsodium, used
   through the existing wrappers. The only new construction is the
   `MLDSAEK1` envelope (§12), which composes `crypto_pwhash` and
   `crypto_aead_xchacha20poly1305_ietf` without modifying either.
2. **Secrets live in `secure_mem` and are wiped on every path**, including
   error paths, exactly as spec-v2 Req 4.2 requires of the protocol code.
3. **Constant-time comparison** of every secret-derived value: token hashes,
   code hashes, ticket hashes, MACs, digests. Identity/handle comparison uses
   `sodium_memcmp` after an explicit length check.
4. **Tokens, login codes, recovery codes and enrollment tickets are never
   stored in the clear.** Tokens, codes and tickets are stored as SHA-256 of
   the value; recovery codes as `crypto_pwhash_str` (Argon2id). A stolen
   database yields no usable bearer secret.
5. **A login code is single-use, expires in ≤ 60 s, and is bound** to
   `{user, handle, handshake_id, SHA-256(state)}`. `EXCHANGE` MUST present the
   same `state` the code was issued against.
6. **Uniform responder flow.** An unknown, revoked, superseded or disabled
   identity MUST produce the same observable message sequence as a valid
   identity whose ClientAuth signature fails (§7.3).
7. **No silent key rotation** (inherited verbatim from spec-v2 Req 7).
   Re-registration of an existing handle with a different public key is
   rejected **and logged**. The logging half is this document's obligation —
   spec-v2 delegated it to the integrator and no integrator implemented it.
8. **Rotation requires proof of possession of both keys**: a valid signature
   by the outgoing key and by the incoming key, over a digest that includes
   the `handshake_id` of the session carrying it (§6.3).
9. **Revocation is immediate.** A revoked device MUST fail the next handshake,
   its tokens MUST be deleted, and its live connections MUST be closed.
10. **Identity keys are encrypted at rest** (§12). No plaintext secret key is
    written to disk by any daemon or CLI command.
11. **Local API callers are authenticated by peer credentials**, not by a
    shared secret: `SO_PEERCRED`/`LOCAL_PEERCRED` uid against an allowlist,
    plus filesystem permissions. Administrative commands are refused on the
    site socket.
12. **The client address used for rate limiting is obtained from a source the
    client cannot forge** (§7.2), and a missing or unverifiable address fails
    closed.
13. **Logging never contains** key material, shared secrets, session keys,
    signatures, nonces, raw frames, decrypted payloads, tokens, login codes,
    recovery codes or tickets. There is no option to enable any of them (§15).
14. **Every store mutation is a single transaction**, and a partially applied
    lifecycle change is impossible (§9.3).

## 6. Application messages

Carried as the **content** of spec-v2 records (§6.4). The record layer supplies
confidentiality, integrity, ordering and replay protection; nothing here
repeats that work.

```
content = op (1 byte) || body
```

Decoding is **strict**, exactly as spec-v2 §6.3.4: exact lengths, full
consumption, no trailing bytes, one op per record. Any violation is a terminal
error; the daemon replies `ERROR` where it can and closes.

| op | name | direction | when |
|---|---|---|---|
| `0x10` | `LOGIN_CODE` | daemon → client | first daemon record after the handshake |
| `0x11` | `ROTATE` | client → daemon | established session only |
| `0x12` | `ROTATE_ACK` | daemon → client | reply to `ROTATE` |
| `0x1F` | `ERROR` | daemon → client | any refusal |
| `0x20` | `BYE` | either | clean close |

The demo protocol's ops (`0x01` MSG, `0x02` ECHO, `0x03` GOODBYE) are **not**
served by the daemon; a record carrying one is an application-protocol error.

### 6.1 Size bounds

The daemon tightens spec-v2 §6.5.1's record maximum, because it never needs
65 KiB records and a smaller cap means smaller fixed per-connection buffers:

```
AUTHD_MAX_CONTENT = 9216 bytes
AUTHD_MAX_RECORD  = SESSION_RECORD_LEN(9216, 4096) = 12313 bytes
```

The largest message is `ROTATE` at **8612** bytes of content (§6.3), so the cap
has ~600 bytes of headroom. A receiver MUST size its plaintext buffer from
`AUTHD_MAX_RECORD`, never from expected content (spec-v2 §6.4's `pt_cap` rule,
and the mistake V2-6 made). A record larger than `AUTHD_MAX_RECORD` is refused
before any AEAD work.

### 6.2 `LOGIN_CODE` (0x10)

The daemon's **first** record after the handshake. Spec-v2 §6.4.4 allows the
responder's confirmation record to carry content; this is that record, so
confirmation and the login code are the same message.

| off | field | bytes | rule |
|---|---|---|---|
| 0 | `version` | 1 | `0x01` |
| 1 | `flags` | 1 | bit0 `rotation_due`; all other bits 0 |
| 2 | `code` | 32 | random (`randombytes_buf`) |
| 34 | `code_expires` | 8 | unix seconds, big-endian |

Content = 43 bytes → a **281-byte record** at the default bucket 256.

The client MUST require this exact op as the first record; anything else is a
protocol error and the session is abandoned.

### 6.3 `ROTATE` (0x11)

Replaces the device's active key with a new one, keeping the handle. Permitted
only on an established, peer-confirmed session, and only for the handle that
authenticated that session.

| off | field | bytes | rule |
|---|---|---|---|
| 0 | `version` | 1 | `0x01` |
| 1 | `flags` | 1 | bit0 = revoke this handle's other tokens on commit; others 0 |
| 2 | `handle_len` | 1 | MUST equal the session's authenticated id length |
| 3 | `handle` | N | MUST equal the authenticated peer id, `sodium_memcmp` |
| 3+N | `pk_new` | 1952 | the incoming ML-DSA-65 public key |
| 1955+N | `sig_old_len` | 2 | big-endian, 1..3309 |
| 1957+N | `sig_old` | L1 | signature by the **outgoing** key |
| 1957+N+L1 | `sig_new_len` | 2 | big-endian, 1..3309 |
| 1959+N+L1 | `sig_new` | L2 | signature by the **incoming** key |

With a 34-byte handle and maximum signatures the body is **8611** bytes and the
content **8612**.

Both signatures cover the same tuple under different labels:

```
M       = handshake_id (16) || flags (1) || handle_len (1) || handle
          || pk_old (1952) || pk_new (1952)
sig_old = Sign(sk_old, SHA-256("mldsa-authd/v1/rotate-old" || 0x00 || M))
sig_new = Sign(sk_new, SHA-256("mldsa-authd/v1/rotate-new" || 0x00 || M))
```

`pk_old` is not transmitted — it is the key that authenticated this session, so
including it in the digest binds the message to one exact old→new edge.
`handshake_id` binds it to this session, so a captured `ROTATE` is useless
elsewhere (Req 8). The two labels stop a signature from either key being
replayed as the other.

**Acceptance order** (first failure wins, nothing is written until all pass):
session confirmed → strict decode → handle equals the authenticated id →
`pk_new` ≠ `pk_old` → `pk_new` unused by any device, in any state → verify
`sig_old` against the session's key → verify `sig_new` against `pk_new` →
re-read the store and confirm device and user are still active → one
transaction (§9.3).

### 6.4 `ROTATE_ACK` (0x12)

| off | field | bytes |
|---|---|---|
| 0 | `version` | 1 (`0x01`) |
| 1 | `handle_len` | 1 |
| 2 | `handle` | N |
| 2+N | `fp_new` | 32 (SHA-256 of `pk_new`) |
| 34+N | `rotated_at` | 8 (unix seconds, big-endian) |

No signature: the record layer already authenticates it under keys only the two
parties hold.

### 6.5 `ERROR` (0x1F) and `BYE` (0x20)

`ERROR` body: `version (1) || code (1)`. Codes are coarse by design — a remote
peer learns that it failed, not why: `0x01` malformed, `0x02` not permitted in
this state, `0x03` rejected, `0x04` rate limited, `0x05` internal. `BYE` has an
empty body.

## 7. Connection binding

### 7.1 Transport

Clients reach the daemon as a **WebSocket** through the site's TLS reverse
proxy. The WebSocket payload carries the existing 4-byte length-prefixed frame
stream unchanged, so one reassembler serves both the WebSocket listener and a
raw listener, and message boundaries on input are irrelevant. The daemon sends
exactly one protocol frame per binary WebSocket message.

The login URL carries an opaque `state` value the site placed in its pre-login
session: `wss://site.example/authd/v1?state=…`, ≤ 64 bytes. The daemon binds
`SHA-256(state)` into the login code (§6.2) and `EXCHANGE` must present the
same value (Req 5). This is what prevents a login-CSRF at the exchange step.

### 7.2 Client address

Rate limiting needs the client's address, and the daemon only ever sees the
proxy. Two mechanisms, in order of preference:

1. **PROXY protocol v2**, which the proxy prepends before any client byte.
   The client cannot forge it because it never gets to write first. Measured
   available in the stock Caddy binary (V4-2 S5).
2. **A single proxy-set header** (`X-Real-IP`), used only when the listener is
   a **Unix socket** whose peer credentials identify the proxy (Req 11).
   `X-Forwarded-For` is never used: it is a client-appendable list. Measured:
   Caddy overwrites a client-supplied `X-Real-IP` and can strip
   `X-Forwarded-For` (V4-2 S4).

A missing or unverifiable address **fails closed** (Req 12).

### 7.3 Uniform responder flow

For an unknown, revoked, superseded or disabled identity the daemon pins a
**decoy public key** — a real ML-DSA-65 public key generated once at
initialisation whose secret was discarded — and proceeds normally. The
`ServerHello` is produced and signed as usual; the handshake then fails at
`ClientAuth` with the same status, the same message count and the same close
point as a valid identity presenting a wrong signature (Req 6).

This costs one signature per probe, which is the rate limiter's problem, and it
is the only way to close the enumeration channel without changing the verified
handshake code.

## 8. Local socket protocol

Two Unix sockets. One request per line, one response per request, at most one
request in flight per connection.

```
request  = CMD SP key=value (SP key=value)* LF        ≤ 8192 bytes
response = "OK" (SP key=value)* LF  |  "ERR" SP "code=" name LF
list     = ("OK" SP "count=" n LF) item* "END" LF
```

Binary values are lowercase hex (a public key is 3904 hex characters, which is
why the line limit is 8192). Labels and reasons are hex too, so there are no
escaping rules at all. Unknown keys, duplicate keys, a missing required key or
a malformed value are `ERR code=malformed`.

**`site.sock`** — mode 0660, group = the site's group, uid allowlist:

| Request | Response |
|---|---|
| `ENROLL user= handle= pk= label= via=site\|recovery [ticket=]` | `OK fp=` / `ERR code=exists-different-key\|pk-in-use\|bad-handle\|user-disabled\|ticket-invalid\|role-mismatch`; a byte-identical re-enrollment is `OK fp= idempotent=1` |
| `EXCHANGE code= state=` | `OK token= user= handle= role= issued= expires=` / `ERR code=unknown\|expired\|used\|state-mismatch` |
| `VERIFY token=` | `OK user= handle= role= issued= expires=` / `ERR code=unknown\|expired\|idle-expired\|device-revoked\|user-disabled` |
| `LOGOUT token=` | `OK deleted=0\|1` |
| `REVOKE-TOKENS user= [handle=]` | `OK count=` |
| `REVOKE-DEVICE handle= reason=` | `OK` / `ERR code=unknown` |
| `LIST-DEVICES user=` | `OK count=` then `DEVICE handle= label= status= enrolled= last_seen= fp=` … `END` |
| `RECOVERY-ISSUE user= count=` | `OK codes=c1,c2,…` (returned once, never again) |
| `RECOVERY-USE user= code= [revoke=all\|none]` | `OK ticket= expires=` / `ERR code=invalid\|locked\|user-disabled` |
| `PING` | `OK version= schema= uptime=` |

**`admin.sock`** — mode 0600, root only: everything above plus
`ENROLL-OPERATOR`, `DISABLE-USER user= reason=`, `ENABLE-USER user=`,
`LIST-USERS`, `AUDIT-TAIL n=`, `BACKUP path=`.

Operator enrollment is impossible from the site's uid **by construction**, not
by a flag (Req 11). Every request is logged with the peer's uid and pid.

## 9. The store

SQLite, pinned by version and SHA3-256 and built in-tree like libsodium;
`SQLITE_THREADSAFE=0`, `SQLITE_OMIT_LOAD_EXTENSION`, `SQLITE_DQS=0`, WAL,
`synchronous=FULL`, prepared statements only, no string-built SQL.

### 9.1 Schema

```sql
meta(key TEXT PRIMARY KEY, value BLOB)          -- schema_version, store_id(16), decoy_pk(1952)
users(user_id BLOB PRIMARY KEY, role TEXT CHECK(role IN('operator','user')),
      status TEXT CHECK(status IN('active','disabled')), created_at INT,
      disabled_at INT, disabled_reason BLOB,
      recovery_fail_count INT DEFAULT 0, recovery_locked_until INT DEFAULT 0)
devices(handle BLOB PRIMARY KEY, user_id BLOB NOT NULL REFERENCES users(user_id),
        label BLOB, status TEXT CHECK(status IN('active','revoked')),
        enrolled_at INT, enrolled_via TEXT, enrolled_by TEXT,
        revoked_at INT, revoked_by TEXT, revoked_reason BLOB, last_seen INT)
device_keys(key_id INTEGER PRIMARY KEY, handle BLOB NOT NULL REFERENCES devices(handle),
            pk BLOB UNIQUE, pk_fp BLOB UNIQUE,
            status TEXT CHECK(status IN('active','superseded','revoked')),
            valid_from INT, valid_to INT, superseded_by_hsid BLOB)
CREATE UNIQUE INDEX one_active_key ON device_keys(handle) WHERE status='active';
login_codes(code_hash BLOB PRIMARY KEY, user_id BLOB, handle BLOB, handshake_id BLOB,
            state_hash BLOB, issued_at INT, expires_at INT, used_at INT)
tokens(token_hash BLOB PRIMARY KEY, user_id BLOB, handle BLOB, handshake_id BLOB,
       issued_at INT, expires_at INT, idle_expires_at INT, last_verified_at INT)
recovery_codes(code_id INTEGER PRIMARY KEY, user_id BLOB, pwhash_str TEXT,
               issued_at INT, used_at INT, used_from TEXT)
enroll_tickets(ticket_hash BLOB PRIMARY KEY, user_id BLOB, issued_at INT,
               expires_at INT, used_at INT)
audit(seq INTEGER PRIMARY KEY, at INT, event TEXT, user_id BLOB, handle BLOB,
      detail TEXT, prev_mac BLOB, mac BLOB)
```

### 9.2 Invariants

1. At most one `active` key per handle (enforced by the partial unique index,
   not by application logic).
2. A public key is unique across all devices and all states, forever: a revoked
   key can never be re-enrolled anywhere.
3. `lookup(handle)` returns a key only when the key is `active`, the device is
   `active` and the user is `active` — one query, three joins.
4. The audit log is append-only and chained:
   `mac_i = crypto_auth(key_audit, prev_mac || seq || at || event || 0x00 || fields)`
   with `key_audit = HKDF-SHA256(ikm = the envelope KEK, salt = store_id,
   info = "mldsa-authd/v1/audit-mac")`, MAC width 32 bytes. The head MAC is
   written to the system journal periodically, so truncation is detectable from
   a second trust domain.

### 9.3 One transaction per operation

Enrollment, rotation, revocation, disable/enable, code issue and code use are
each exactly one SQLite transaction (Req 14). Rotation, the only multi-row
case, inserts the new key `active`, sets the old to `superseded` with
`valid_to` and `superseded_by_hsid`, optionally deletes the handle's other
tokens, and appends the audit row — all or nothing.

## 10. Lifecycle

### 10.1 Enrollment

**Operators (A).** The operator runs `authd_client keygen` on their own
machine, which generates a handle and keypair and writes `<handle>.ek` (§12)
and `<handle>.pub` (`MLDSAPK1`). The `.pub` is copied to the host; an
administrator runs `authd_admin enroll-operator`. The secret never moves.

**End users (B).** The browser generates the handle and keypair, seals the key
under a passphrase, and POSTs the public key to the site over the site's own
authenticated TLS session; the site calls `ENROLL … via=site`. The site is
already the authority on who may have an account, so making it the enroller
adds no trust. An unauthenticated enrollment flow at the daemon is **not**
provided: it would require an anonymous identity mode the protocol does not
have, and would expose an unauthenticated write path to the internet.

Re-enrollment of a known handle with a different key is **rejected and
audited** (Req 7). With an identical key it is idempotent.

### 10.2 Rotation

Specified in §6.3. The client writes the sealed new key to `<handle>.ek.next`
**before** sending `ROTATE`, and renames it over the current file on
`ROTATE_ACK`. If `.ek.next` exists at startup the client tries it first: if it
authenticates, the rename was interrupted and is completed; if it is unknown,
the server never committed and the old key is still current. There is no
overlap window in which two keys authenticate.

Tokens survive rotation (they are bound to the handle) unless `flags` bit 0 is
set, which is the "I think this key leaked" path.

### 10.3 Revocation and recovery

| Operation | Effect | Live sessions | Tokens |
|---|---|---|---|
| `REVOKE-DEVICE` | device and its active key → `revoked` | closed | deleted |
| `REVOKE-TOKENS` | — | — | deleted |
| `DISABLE-USER` | user → `disabled`; every device fails lookup | closed | deleted |
| `ENABLE-USER` | user → `active`; devices keep their own status | — | — |

Revocation takes effect at the next handshake immediately (the store is
authoritative, there is no key cache) and at the site within its `VERIFY`
cache TTL, which SHOULD be ≤ 30 s or absent.

**Recovery codes.** `RECOVERY-ISSUE` generates 1..16 codes of 10 random bytes
rendered as 16 base32 characters (80 bits), returned once and stored as
`crypto_pwhash_str` (Argon2id, ops 2, memory 64 MiB — the entropy is the
defence; the KDF bounds server memory per verification). `RECOVERY-USE`
verifies against each unused code, marks it used (never deletes it), and
returns a single-use **enrollment ticket** valid 10 minutes, which the site
presents to `ENROLL … via=recovery`. Five failures lock recovery for one hour.

**Device loss with no codes** is site-mediated re-enrollment: the site
authenticates the person by its own means and calls `ENROLL via=site`. This is
logged at WARN as `enroll-without-continuity`, because it is the one path with
no cryptographic continuity at all.

## 11. Tokens

Opaque, 256 bits from `randombytes_buf`, stored as `SHA-256(token)` (Req 4).
Signed or structured tokens are **rejected**: offline verification would need
an ML-DSA implementation in the site's language, and would lose instant
revocation, for no gain — the credential is a bearer either way.

Bound to `{user_id, handle, handshake_id, issued_at, expires_at,
idle_expires_at}`. Defaults: absolute lifetime 12 h (operators 8 h); idle
lifetime 1 h (operators 30 min), refreshed on each successful `VERIFY`.
Expired rows are swept periodically and the count logged.

The token reaches the site through `EXCHANGE`, never through the browser's
JavaScript: the client receives only the single-use login code (§6.2) and hands
that to the site. An XSS that steals the code cannot exchange it — `EXCHANGE`
is available only on the local socket.

## 12. `MLDSAEK1` — identity keys at rest

One envelope format for server, operator and browser keys. All constants below
are libsodium's own, read from the pinned build.

| off | field | bytes | value |
|---|---|---|---|
| 0 | magic | 8 | `"MLDSAEK1"` |
| 8 | `version` | 1 | `0x01` |
| 9 | `kdf_alg` | 1 | `0x01` = Argon2id13 (`crypto_pwhash_ALG_ARGON2ID13` = 2) |
| 10 | `opslimit` | 4 | big-endian; accepted 1..10 |
| 14 | `memlimit` | 8 | big-endian bytes; accepted 8 MiB..1 GiB |
| 22 | `salt` | 16 | `crypto_pwhash_SALTBYTES`, fresh per write |
| 38 | `aead_alg` | 1 | `0x01` = XChaCha20-Poly1305-IETF |
| 39 | `nonce` | 24 | `..._NPUBBYTES`, fresh per write |
| 63 | `ct_len` | 4 | big-endian = plaintext + 16 (`..._ABYTES`) |
| 67 | ciphertext ‖ tag | `ct_len` | |

**Bytes [0, 67) are the AEAD's associated data.** This is why an AEAD is used
rather than `crypto_secretbox`: a secretbox authenticates nothing outside the
box, so an attacker could rewrite `memlimit` to 1 GiB and turn every start-up
into a memory exhaustion. The bounds close that anyway; binding the header
costs nothing and closes it twice.

The plaintext is the **exact `MLDSASK2` image** (`6025 + id_len` bytes,
including its own integrity digest), so the existing loader validates it
unchanged after decryption. Total file size = `6108 + id_len`; for a 34-byte
handle, **6142 bytes**.

**Parameters by role:** server `ops=4, mem=256 MiB`; operator `ops=3,
mem=256 MiB`; browser `ops=3, mem=64 MiB` (measured at 111.5 ms in wasm,
V4-2 S6). Parameters live in the header, so they are tunable per file without
a format change.

**Load order** mirrors `demo_keys_load_identity`: custody (`O_NOFOLLOW`,
regular file, owner == euid, `mode & 077 == 0`) → size bounds → magic and
version → algorithm ids → parameter bounds → KDF → AEAD open into
`secure_mem` → `MLDSASK2` parse with its digest and id checks → sign/verify
self-test. The passphrase and derived key are wiped immediately.

**Server passphrase delivery** on a headless host: 32 random bytes from
`authd_admin init`, delivered by systemd `LoadCredentialEncrypted`
(TPM-bound where available), with `LoadCredential` as the fallback. Never an
environment variable, never argv. Argon2id is then a wrapper around an already
uniform secret, not the defence — which is why the honest claim is narrow:
encryption at rest keeps the key out of **disk images, snapshots and backups**,
and does nothing against root on a running host.

Writing follows V2-9's rules: a temporary file with `O_EXCL`, `fsync`, then
`link()` — never in place, never clobbering. `migrate-key` converts an existing
`MLDSASK2` file and leaves the source untouched, printing that the plaintext
should be destroyed once the new file is verified.

## 13. Command-line interfaces

`authd_admin`: `init`, `keygen-server`, `migrate-key`, `rewrap`,
`enroll-operator`, `disable-user`, `enable-user`, `list-users`,
`list-devices`, `audit-tail`, `backup`, `--check-config`.

`authd_client`: `keygen`, `login`, `rotate`. `login` prints the login code as
base64url for pasting into the site's form (milestone A has no browser).

Exit codes: 0 success, 1 operation failed, 2 usage error, 3 configuration
error. Every failure prints a status name from the same enums the daemon logs.

## 14. Browser client *(B)*

Feasibility was established before this section was written (V4-2 S6): the
pinned liboqs and libsodium build under Emscripten, and the project's own KAT
suite produces **27 checks in wasm identical to 27 native**, including both
ML-DSA-65 and ML-KEM-768 known-answer hashes. The login-critical path measures
0.556 ms and Argon2id(3, 64 MiB) 111.5 ms. No fallback backend is adopted.

Architecture: the protocol C code compiled to wasm with an explicit export
list; a thin JavaScript transport that moves bytes between the module and a
WebSocket; IndexedDB holding `{handle, MLDSAEK1 envelope, pinned server
MLDSAPK1}` with `navigator.storage.persist()`. **No cryptography in
JavaScript.** The secret key is opened into wasm memory only to sign
`ClientAuth` and wiped immediately after; it is not needed for the session.
The wasm build requires `-sSTACK_SIZE=8MB` — the 64 KiB default faults
immediately on this codebase's 4 KB keys.

**Honest limits, which the enrollment page states, not only this document:**
an XSS on the origin can read wasm memory while the key is unlocked and can
exfiltrate the sealed blob for offline guessing (Argon2id slows that; a weak
passphrase still loses, so a minimum length is enforced); there is no hardware
backing; browsers may evict storage; a copied blob is an undetectable clone
(ML-DSA is stateless and no signature counter exists). An OS passkey store
cannot hold an ML-DSA key today.

## 15. Logging

One `key=value` line per event to stderr (journald). Fields: `ev`, `conn`,
`src` (per `log_client_ip`), `id` (escaped, per `log_identities`), `stage`,
`status`, `ms`, `rx`, `tx`.

**Never logged** (Req 13): keys, shared secrets, session keys, signatures,
nonces, raw frames, decrypted payloads, tokens, login codes, recovery codes,
tickets. There is no option to enable any of them.

**Always logged**: every enrollment and every Req 7 rejection (with both key
fingerprints), every rotation (`handle`, `fp_old`, `fp_new`, `handshake_id`),
every revocation and user status change with actor and reason, recovery issue
and use (success or failure, never the code), login-code issue and exchange,
logout, and the sweep counts.

Device handles are pseudonymous but, for public users, are personal data:
`log_identities` and `log_client_ip` control them, and the defaults for
milestone B are narrower than for A.

## 16. Deployment

User `mldsa-authd`, never root. `/var/lib/mldsa-authd/` mode 0700 holds
`store.sqlite3`, `server.ek`, `server.pub` and `backups/`;
`/run/mldsa-authd/` holds `site.sock`, `admin.sock` and the proxy-facing
listener. Configuration is a `key = value` file at `/etc/mldsa-authd/authd.conf`
mode 0600, validated by `--check-config` before the service starts.

The systemd unit sets `NoNewPrivileges`, `ProtectSystem=strict`,
`ProtectHome`, `PrivateTmp`, `PrivateDevices`, `ProtectKernel*`,
`ProtectControlGroups`, `ProtectProc=invisible`, `RestrictAddressFamilies=AF_UNIX AF_INET`,
`RestrictNamespaces`, `RestrictSUIDSGID`, `LockPersonality`,
`MemoryDenyWriteExecute`, `SystemCallFilter=@system-service`,
`CapabilityBoundingSet=`, `UMask=0077`, `LimitCORE=0`, and
**`LimitMEMLOCK` derived from the configured slot count**, because libsodium
returns unlocked memory silently when the limit is exhausted (V4-2 S1) — this
is a correctness setting, not a tuning knob.

The binary is built Release with `-fPIE -pie -Wl,-z,relro -Wl,-z,now
-Wl,-z,noexecstack` and a named CPU target (never `-march=native`), and
`tools/audit/check_hardening.sh --require` gates it.

## 17. Limits and targets

| Quantity | Value | Source |
|---|---|---|
| Handshakes per second per vCPU | ~2000 (Release) | spec-v2 §5.1 measurements |
| Pending-ledger capacity | ≤ **2048** | V4-2 S2: 79.6 µs/handshake at 2048, 159.5 µs at 4096 |
| Sustained handshake rate | capacity ÷ TTL | consumed entries are reclaimed only at expiry |
| RSS per in-flight handshake | ~95 KiB | V4-2 S1: 9.5 KiB × ~10 secure blocks |
| `AUTHD_MAX_RECORD` | 12313 B | §6.1 |
| Login code lifetime | ≤ 60 s | Req 5 |

## 18. Known limitations (document, do not silently fix)

- Server identity-key rotation is not specified; it means redistributing pins.
- No HSM or TPM key custody; root on the host has the key.
- A copied browser key blob is an undetectable clone.
- Traffic analysis is only partially mitigated (inherited from spec-v2 §9).
- The store is single-host; there is no replication or failover.
- Recovery ultimately rests on the site's own identity proofing.
- The daemon is single-threaded; capacity is one core's worth (§17 says how
  much that is, and it is ~100× a single site's need).
